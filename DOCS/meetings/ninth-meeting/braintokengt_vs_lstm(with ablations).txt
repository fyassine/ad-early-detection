Good — now I have the exact data flow. Here's the answer, grounded in the code the agent found.

What actually feeds the LSTM

The LSTM never sees the graph, in any arm. encode_batch_sequences (CLASSIFIER/model/GELSTM/utils.py:60) turns each visit into one fixed-width vector, stacks those into a sequence, and only that sequence reaches self.lstm. The recurrent core is graph-agnostic by construction — the only question that varies between arms is how that per-visit vector gets built.

The node features are the FC matrix itself. Each visit's graph comes from a 200×200 whole-brain functional-connectivity matrix (Schaefer-200 atlas, Pearson correlation, z-transformed — CLASSIFIER/model/GELSTM/dataset.py:184). Node i's feature vector is literally that ROI's row of correlations to all 200 other ROIs. So x isn't some separate signal alongside the graph — x is the connectivity data.

The edges are derived from that same matrix, not an independent source. adj = knn_binary_adjacency_matrix_no_diag(torch.abs(feat), k=8) (dataset.py:187) — each ROI connects to its 8 highest-|correlation| partners, and edge_attr is a binary 0/1 mask (correlation magnitude is dropped once it decides which edges exist). So the graph structure is a sparsified, binarized view of x, not new information.

With an encoder: 3 GATv2 layers with FiLM conditioning message-pass over that sparsified 8-nearest-neighbor graph, compressing to a 64-d latent optimized during GAAE pretraining for reconstruction (rebuild x and the adjacency), then mean-pooled.

Without an encoder (none): z = x directly (models.py:213), mean-pooled over the 200 ROIs → a 200-d vector that's literally the column-mean of the FC matrix — a global "average connectivity profile," no learned transformation, no edges touched at all.

Why none came out ahead

1. No information is actually lost by skipping the encoder — the raw pooled vector is a direct summary of the same connectivity data the GNN would have processed, just without the lossy steps in between (kNN sparsification down to 8 edges, binarizing away correlation strength, compressing to 64-d through a bottleneck).
2. The GNN's bottleneck is optimized for the wrong objective. GAAE pretraining targets reconstruction fidelity (rebuild the graph), not conversion prediction. If AD-relevant variance isn't important for reconstruction, the encoder has no incentive to preserve it through the 64-d bottleneck — mean-pooling the raw 200-d row, by contrast, can't discard anything, since there's no learned compression step at all.
3. Small-sample instability compounds it. none trains only 31K params vs. 966K for random/finetuned. On ~130 training subjects with a handful of converters, the heavier encoder is much easier to overfit or destabilize during end-to-end training — which is exactly what you saw: random's highest CV fold-to-fold spread of any arm, and pretrained_finetuned collapsing outright at seed 43 (test AUC 0.421).

So the honest characterization isn't "the graph structure doesn't matter" — it's "for this cohort size, compressing the FC matrix through a sparsified, reconstruction-pretrained GNN bottleneck throws away more signal than it adds, and a parameter-light global summary of the same raw connectivity data is a safer bet."
